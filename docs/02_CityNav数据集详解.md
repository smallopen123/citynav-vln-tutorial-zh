# 02｜CityNav 数据集详解

## 1. CityNav 要解决什么问题

CityNav 面向真实城市三维场景中的**语言引导无人机导航**。它把传统室内 VLN 放大到城市尺度：目标可能在视野之外，建筑外观相似，航程长，而且指令会用道路、建筑、相对方位和属性共同描述目标。

根据 [CityNav 官方仓库](https://github.com/water-cookie/citynav) 和 [ICCV 2025 论文](https://openaccess.thecvf.com/content/ICCV2025/papers/Lee_CityNav_A_Large-Scale_Dataset_for_Real-World_Aerial_Navigation_ICCV_2025_paper.pdf)，数据集包含 **32,637 条目标描述**和 **5,850 个目标对象**，城市三维基础来自 SensatUrban 的真实城市点云。正式使用时请同时记录官方仓库 commit 和下载的数据版本。

## 2. 一条任务可以怎样理解

概念上，一条 CityNav episode 至少连接下面几类信息：

```text
episode = {
  language: 对目标/路线的自然语言描述,
  start: 起始位置与朝向,
  target: 目标对象及其空间位置,
  trajectory: 专家/人类轨迹或用于评测的参考,
  scene: 所属城市区域,
  observations: 运行时由场景和相机位姿生成的 RGB-D
}
```

这段是**概念模式**，不是保证与某个 JSON 的字段名逐字相同。真实文件请用：

```bash
python examples/inspect_citynav.py <某个-json-路径>
```

## 3. 语言指令是什么形式

CityNav 的语言不是 `turn_left, forward` 这样的动作脚本，而是对目标和地理关系的自然语言描述。它可能包含：

- 目标类别或外观：建筑、屋顶颜色、形状、大小；
- 地标关系：在某座楼、道路或区域旁边；
- 空间关系：北侧、后方、相邻、道路另一侧；
- 多个参照物：用组合证据消除城市中相似建筑的歧义。

语言只给语义，不等于直接给模型世界坐标。模型还需要把“图书馆南侧的红顶建筑”落到场景中的具体实体，这一步称为 grounding。

## 4. 官方目录中常见的数据角色

官方 README 所示的数据组织包括：

```text
data/
├─ cityrefer/
│  ├─ objects.json                 # 场景中的目标/地标对象
│  └─ processed_descriptions.json  # 处理后的自然语言描述
├─ citynav/
│  ├─ citynav_train_seen.json
│  ├─ citynav_val_seen.json
│  ├─ citynav_val_unseen.json
│  └─ citynav_test_unseen.json
├─ rgbd/                           # 场景对应的 RGB 与深度栅格/渲染数据
└─ gsam/                           # Grounded-SAM/检测分割产生的语义结果
```

具体文件名会随版本变化，以上用于建立角色对应，不应代替对本地数据的检查。

## 5. 数据划分在测什么

- `train_seen`：用于训练，场景分布对模型可见。
- `val_seen`：验证时仍来自“见过”的场景类型/区域，用于调参与诊断。
- `val_unseen`：验证未见区域，主要测空间和视觉泛化。
- `test_unseen`：最终未见测试，通常不能依赖测试标签调参。

因此“同一个 SR”只有在相同 split 和相同协议下才可比较。seen 高而 unseen 低，往往说明模型记住了场景外观或坐标规律，而没有学会稳健 grounding。

## 6. 每种模态解决什么问题

| 模态 | 回答的问题 | 单独使用的局限 |
|---|---|---|
| 语言 | 要找什么、与什么地标有什么关系 | 不直接给出可靠世界坐标 |
| RGB | 当前看到的建筑/道路是什么 | 无尺度，远处不可见，外观会混淆 |
| Depth | 前方结构多远、几何是否可通行 | 不知道“这栋楼叫图书馆” |
| 位姿/GNSS | 无人机现在位于全局哪里 | 定位误差，且不理解目标语义 |
| OSM/地理数据 | 道路、建筑轮廓及地理拓扑 | 属性不完整、时效/对齐可能有误差 |
| GSM | 把地理位置与语义候选放到统一地图 | 仍可能含误检，不等于安全可执行路径 |
| 历史 | 去过哪里、完成到哪一步、曾相信什么 | 历史太长会带来记忆和计算压力 |

## 7. 为什么得到二维目标坐标后仍需 RGB-D

二维目标坐标只解决“宏观上往哪里去”。它没有保证：

1. 坐标预测完全正确；
2. 当前位置到目标之间没有建筑或高度障碍；
3. 地图与真实视觉严格对齐；
4. 到达附近时能分辨目标与相似邻居；
5. 无人机知道何时安全地 STOP。

可以把导航类比为开车：手机地图给出目的地坐标，但驾驶员仍要看道路、车辆和入口。GSM/目标坐标负责宏观方向，RGB-D 负责在线验证、局部定位和执行安全。

## 8. 适合做的三个数据练习

1. 统计四个 split 的 episode 数、指令长度和轨迹长度分布。
2. 随机抽取 20 条 unseen 指令，手工标注其中的目标属性、地标和空间关系。
3. 将失败样本按“语言歧义、地图缺失、视觉误检、走过不停止、路径过长”分类。

这三项比一开始直接重训大模型更容易暴露数据与协议问题。
